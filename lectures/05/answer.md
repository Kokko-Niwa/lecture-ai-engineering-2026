- 取り組んだレベル：基礎 
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py`の`RAG_TOP_K`を 5→2 に変更
- 比較した質問と、固定した条件（モデル・対象資料など）：質問「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」。モデル`gemini-3.5-flash-lite`、対象＝第1〜3回214ページ、通常のベクトル検索（Tree/Graphなし）。`RAG_TOP_K`以外は変更なし。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  | 項目 | 変更前（TOP_K=5） | 変更後（TOP_K=2） |
  |---|---|---|
  | 入力トークン | 3,027 | 1,740（約43%減） |
  | 出力トークン | 147 | 203 |
  | モデル応答回数 | 2 | 2 |
  | 時間（秒） | 2.84 | 3.13 |
  | 推定コスト（USD） | $0.001276 | $0.001030（約19%減） |
  | 検索1位 / 引用ページ | lec02-main-p052 / 第2回 p.52（QLoRAは p.51,52） | lec02-main-p052 / 第2回 p.52（QLoRAは p.51,52） |
  | 回答の正しさ | 正しい | 正しい（低ランク行列A・B、4bit、メモリ削減まで言及） |

  検索結果の1位が両方とも`lec02-main-p052`（＝答えの根拠p.52）だったため、TOP_Kを2に絞っても必要なページは取得でき、回答の正しさと引用ページは維持されていた。

- 改善した例と、残る失敗・制約：
改善＝余計なページが減り、入力トークン・コストが下がったのに回答は劣化しなかった。  
制約＝各条件1回ずつの実行なので、出力トークンの増加と時間の微増は実行ごとのブレの範囲で断定できない。構造的に確実なのは、入力トークン・コストの減少。  
- 気づき・疑問：
この質問は実質 p.52 の1ページで答えが揃うため、検索件数を5→2に減らしても答えは変わらず、むしろ安くなった。「参照ページ数を増やす＝良い」ではないと実測で確認できた。  
疑問＝根拠が複数ページに散る質問（章をまたぐ比較など）では、TOP_Kを減らすと根拠が落ちて回答が崩れるはず。TOP_Kを下げてよいかは「根拠が1ページに集中しているか」で決まりそう。
